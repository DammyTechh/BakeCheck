# Deployment

**Backend → Render. Frontend → Vercel.**

---

## Why this split

The Node API *could* run on Vercel. The Python vision service cannot:

| Constraint | Why it rules Vercel out |
|---|---|
| Bundle size | OpenCV + NumPy + scikit-learn exceeds the serverless bundle limit |
| Execution time | Image analysis runs for seconds; serverless functions are tuned for milliseconds |
| Cold starts | Every cold invocation would reload OpenCV and the model artifact |
| CPU profile | Analysis is CPU-bound; serverless pricing and limits assume I/O-bound work |

Splitting the two across providers would also put a public internet hop
between the API and a service that is supposed to be private. Both run on
Render, on the same private network.

---

## 1. Database

Either Render PostgreSQL (provisioned by `render.yaml`) or an existing
Supabase project.

### Using Supabase

Take the **session pooler** connection string from
Project Settings → Database:

```
postgresql://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

Set `DATABASE_SSL=true`. Supabase terminates TLS with a certificate that is
not in Node's default trust store, which the pool already accounts for.

### Row Level Security

Migration `0006` enables RLS and defines policies that scope every row to the
caller's laboratory. These are **defence in depth**, not the primary control —
the API enforces the same rule in its guards and queries, and both layers must
agree.

The API sets two session variables per request, inside the transaction:

```sql
SET LOCAL app.current_user_id   = '<uuid>';
SET LOCAL app.current_user_role = 'LAB_TECHNICIAN';
```

`SET LOCAL` is deliberate: the setting is discarded when the transaction ends,
so a pooled connection cannot carry one user's identity into the next user's
request.

> The Supabase **service-role key bypasses RLS entirely**. It is backend-only.
> It must never appear in a frontend bundle, a client-side environment
> variable, or anything prefixed `VITE_` / `NEXT_PUBLIC_`.

## 2. Object storage

Render's filesystem is **ephemeral** — a redeploy destroys it, and uploaded
images go with it. Production must use `STORAGE_DRIVER=supabase`.

The API logs an error at startup if it finds `STORAGE_DRIVER=local` with
`NODE_ENV=production`, because the failure is otherwise silent until the first
redeploy.

### Creating the bucket

1. Supabase → Storage → New bucket
2. Name: `sample-images`
3. **Public: off.** This is confidential laboratory data.
4. No RLS policies are needed — the service-role key bypasses them, and all
   access is mediated by the API.

Reads are served through short-lived signed URLs (300 s by default). No
permanent public URL is ever issued.

## 3. Deploying to Render

### Blueprint

1. Push the repository to GitHub.
2. Render → **New** → **Blueprint** → select the repository.
3. Render reads `render.yaml` and proposes three services plus a database.
4. Fill in the variables marked `sync: false`:

| Variable | Value |
|---|---|
| `CORS_ORIGINS` | Your exact Vercel origin, e.g. `https://breadguard.vercel.app` |
| `APP_BASE_URL` | Same |
| `SUPABASE_URL` | `https://<ref>.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | From Supabase → Settings → API |
| `REFRESH_COOKIE_DOMAIN` | Apex domain, or leave blank |
| `RESEND_API_KEY` | Optional |
| `EMAIL_FROM` | Optional |

Everything else — including both JWT secrets and the internal AI key — is
generated by Render. The internal key is generated **once** on the AI service
and referenced by the API via `fromService`, so the two always agree and the
secret is never written down.

### After the first deploy

Run the migration job from the dashboard:

> `breadguard-migrate` → **Trigger Run**

It is scheduled for 31 February, which never occurs, so it only ever runs when
triggered by hand.

> **Do not run the seed in production.** It refuses to run with
> `NODE_ENV=production`, but do not try.

### Verify

```bash
curl https://breadguard-api.onrender.com/health
curl https://breadguard-api.onrender.com/health/ready
```

`health/ready` reports each dependency. It returns 200 when the database is
reachable even if the vision service is not — the API can still serve samples
and history without it, and failing readiness would pull the whole application
out of rotation for a partial outage.

## 4. Frontend on Vercel

```bash
# Project settings
Framework preset:  Vite
Root directory:    apps/web
Build command:     npm run build
Output directory:  dist
Install command:   npm install
```

Environment variable:

```
VITE_API_BASE_URL=https://breadguard-api.onrender.com/api/v1
```

> Only `VITE_`-prefixed variables reach the browser bundle — which is exactly
> why no secret may ever carry that prefix. The Supabase service-role key, the
> JWT secrets and the AI internal key are backend-only.

### Cross-site cookies

Frontend and API are on different origins, so the refresh cookie must be
`SameSite=none`, which browsers only accept with `Secure`. `render.yaml` sets
both. The CORS allowlist must name the Vercel origin **exactly** — the
configuration refuses wildcards in production, because `credentials: true`
with a wildcard origin is unsafe.

### Camera access

`getUserMedia` requires a secure context: HTTPS, or `localhost`. Vercel serves
HTTPS, so production is fine. For testing on a phone against a local dev
server, use a tunnel rather than an IP address — `http://192.168.x.x` is not a
secure context and the camera will not start.

## 5. Production checklist

### Secrets

- [ ] `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` generated, ≥ 32 chars, **different**
- [ ] `AI_SERVICE_INTERNAL_KEY` generated, matches `AI_INTERNAL_KEY`
- [ ] No placeholder values anywhere (the app refuses to start with them)
- [ ] Service-role key present on the backend only
- [ ] `.env` is not committed

### Transport and cookies

- [ ] `COOKIE_SECURE=true`
- [ ] `COOKIE_SAMESITE=none` for a cross-origin frontend
- [ ] `CORS_ORIGINS` lists exact HTTPS origins, no wildcard
- [ ] `TRUST_PROXY=true` behind Render's load balancer
- [ ] `DATABASE_SSL=true`

### Exposure

- [ ] AI service deployed as `pserv` — **no public route**
- [ ] `AI_DOCS_ENABLED=false`
- [ ] `SWAGGER_ENABLED=false`, or behind authentication at the ingress
- [ ] Storage bucket private
- [ ] `STORAGE_DRIVER=supabase`, not `local`

### Data

- [ ] Migrations applied (`db:migrate:status` shows none pending)
- [ ] Seed **not** run
- [ ] Database backups enabled
- [ ] At least one real administrator account created

### Operations

- [ ] `/health` and `/health/ready` wired to monitoring
- [ ] Log aggregation collecting both services
- [ ] `npm audit --omit=dev` clean
- [ ] Rate limits reviewed for expected traffic

### Scientific

- [ ] Reference charts reviewed; illustrative data not marked `VALIDATED`
- [ ] Test methods carry real procedure references
- [ ] Users told that results are screening estimates
- [ ] `docs/prototype-limitations.md` shared with the laboratory

## 6. Scaling

**Scale the AI service by adding instances, not workers.** Each uvicorn worker
loads its own copy of OpenCV and the model, so several in one container
multiplies memory for no throughput gain on CPU-bound work.

`AI_SERVICE_MAX_CONCURRENCY` on the API caps in-flight analyses. Keep it at or
below the AI service's own `AI_MAX_CONCURRENCY` across all instances;
exceeding it only queues requests at the slower end.

The database connection pool (`DATABASE_POOL_MAX`, default 10) is per API
instance. With Supabase's pooler, total connections across instances must stay
within the plan's limit.

---

## 7. Rolling back

- **Application**: Render keeps previous deploys; roll back from the dashboard.
- **Database**: migrations are forward-only by design. There is no automatic
  down-migration, because a down-migration that drops a column destroys data
  that the previous release wrote. Roll forward with a new migration.
- **Model**: `POST /api/v1/ai/models/{id}/rollback` reactivates the previous
  version. Results produced by the withdrawn model keep their recorded model
  name and validation state — history stays honest about what produced it.
